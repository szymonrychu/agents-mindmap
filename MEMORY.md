## 2026-11-12 - embedder, hybrid search, reembed, golden set (research-mindmaps Task 21)

- Query form: `Instruct: Given a search query, retrieve relevant passages that answer the query\nQuery: <q>` (`embeddings.QUERY_PREFIX`), passages unprefixed. The spec and plan say a `query: ` prefix, which is the plain e5 convention; multilingual-e5-large-instruct expects the instruction form (model card) and the TEI spike measured recall@10 0.983 / MRR 0.956 with exactly this text. A different prefix changes only query vectors, so it can be changed without `reembed`.
- No transaction across the model call: `claim_pending` (FOR UPDATE SKIP LOCKED, 4 nodes) commits before `embed`; `store_chunks` runs in a new transaction whose `UPDATE nodes SET embedded_rev = content_rev WHERE id AND content_rev = <claimed> AND embedded_rev < content_rev` is the status guard; no row means stale, nothing written, the node stays pending and the next pass retries it. The embedder never touches `version`, so it never causes a client 409.
- `node_embedded` events carry actor `system:embedder` (the `events.actor` column has no CHECK) and stay silent for notices.
- Every growth area counts in chunk 0 whatever its status: a status change does not bump `content_rev`, so filtering on status would leave chunk 0 stale.
- Chunker: `approx_tokens` counts words and punctuation, a long word one token per 4 chars (conservative for XLM-R sentencepiece on Polish). Runs over 400 chars are cut. Overlap is the previous chunk's tail of at least 50 tokens, only inside one section.
- Semantic SQL: the inner query orders by distance alone (so the HNSW index serves it) with `LIMIT 50`; the outer query breaks ties on node id and ord for determinism. Vectors go in as the pgvector text literal (`%s::vector`), no adapter registration on pool connections. `hnsw.ef_search` and `statement_timeout` are `set_config(..., true)` inside the read guard.
- Degradation: the API embeds the query before taking a connection, `asyncio.timeout(embeddings.QUERY_TIMEOUT_SECONDS)` (2 s); `EmbedderUnavailable` or timeout gives `semantic: false` and lexical lists, also for `mode=semantic`. `semantic` is true only when a query vector was used.
- Backoff: the first wait is `MINDMAP_EMBEDDER_POLL_SECONDS`, doubling to `MINDMAP_EMBEDDER_BACKOFF_MAX_SECONDS`; a NOTIFY does not cut a backoff short (private event). Any provider error backs off globally (a node that always fails would stall the queue; none known with TEI, whose input truncation covers long chunks).
- Metrics: `prometheus-client` on its own registry, served by the embedder process on `MINDMAP_METRICS_PORT` (9102). The chart declares no port on the embedder (no scrape config exists in the cluster yet; `test_notifier_and_embedder_deployments_behind_flags` asserts workers have no ports); read with `kubectl exec ... python -c "urllib.request.urlopen('http://127.0.0.1:9102/metrics')"`.
- Orchestrator token optional in Settings (fixed latent Task 11 bug): agents-common `BaseServiceSettings._token_from_file` requires it, so the chart's `migrate` init container and the embedder (both given only the database, secrets invariant 9) would have exited 78. `Settings` overrides the validator by name (file still read), and `serve-*` and `notifier` require the token in the cli.
- `notifier._sleep`/`_wake_on_notify` moved to `loop.py` (`sleep_or_wake`, `wake_on_notify`), shared with the embedder.
- Golden set: the 30 spike passages as nodes, 28 queries (12 spike questions, 16 keyword). Lexical search ANDs every word, so questions score about 0.1 lexical recall; the set is half keyword queries so the plan's fake lexical floors (recall@10 0.5, MRR 0.3) measure the harness. Fake numbers: lexical 0.551 / 0.679, hybrid 0.926 / 0.982. Live numbers: pending (`eval/run.py --embedder-url`, floors 0.7 / 0.5).
- `tests/test_cli.py` IMPLEMENTED now lists `embedder` and `reembed` (its LATER tuple was the Task 21 placeholder).

## 2026-11-12 - actors, growth areas, edges, links, directions, knowledge (research-mindmaps Task 9)

- `Actor` (api/actors.py) is resolved by one dependency (`state.resolve_actor`): `user_actor` on web and delegate (identity headers as Task 8), `agent_actor` on the service listener (`X-Orch-Session` required, `X-Orch-Projects` `*` or 1..10 distinct slugs, home first; malformed is 400 `actor_required`). Author is `user:<email>` or `session:<slug>` (session id when the slug header is absent); `events.actor_session` is the session id.
- Reads: lists and the edge/link/direction filters use the active project list for every actor; key reads are unscoped for users (spec 3.5, archived projects included, Task 8 ruling) and 404 for agents on an inactive project. Writes: 404 for an unknown key first, then 403 `project_forbidden` before any write (scope lookups in `db/scope.py`; agents never see row counts change). Edge create needs write on the source and the destination in the active list; delete needs write on either end; one event per map an edge touches.
- The service app mounts the same routers with `agent=True`: no hard delete of maps, nodes or growth areas (DELETE answers 405); edge and link deletes stay.
- A direction's `task` becomes a link with relation `researched_by` (on the node when the direction names one, else the map); seed growth areas go on the named node or the map root and carry `direction_id`. Withdraw by an agent needs `origin='agent'` and `created_by` equal to its author (403 `withdraw_forbidden`).
- Growth area text changes (and add or delete) bump the node `content_rev` but not `current_version`; reorder renumbers siblings contiguously from a zero-based `position`. PATCH takes explicit `null` for `task_key` and `grown_node` (cleared), and a `grown_node` must be in the same project and the status `grown`.
- Node create publishes growth areas, links and edges in one transaction; a repeated `client_key` returns the first node and adds nothing. Knowledge notes create the project's knowledge map lazily under `pg_advisory_xact_lock(hashtext('knowledge:<project>'))`.
- `GET /nodes/{key}` now carries growth areas, edges (both ends in active projects), links and open or acknowledged directions.

## 2026-11-12 - schema, maps, nodes (research-mindmaps Task 8)

- `0001_mindmap.sql` hardcodes `vector(1024)` and the seeded `embedding_config` row (a static .sql cannot read Python); `test_sql_dim_matches_constant` ties them to `EMBED_DIM`/`EMBED_MODEL`. Provisional until the TEI spike (Task 20) confirms; changing it before the first deploy edits 0001, after it needs a new migration plus `reembed`. `serve` refuses to start on a mismatch (`verify_embedding_config`, names `MINDMAP_EMBED_DIM` / `MINDMAP_EMBEDDER_MODEL`).
- Tests: the session container's `template1` carries `vector` (CNPG does this at bootstrap); `bare_db_url` clones `template0` for the guard test.
- Two counters on a node: `version` is the optimistic row guard sent by clients on every PATCH (bumped by any change); `current_version` is the latest `node_versions` row (bumped only by a topic or notes change). A PATCH locks the row (`FOR UPDATE`), so a concurrent loser sees the new version and answers 409 `version_conflict` with `version` (the row guard, same name as the request field) in the error body; `current_version` only ever means the note version. `content_rev` is kept next to `current_version` on purpose (2026-11-12): the spec bumps it for growth-area text changes too (embedding drive), so the two diverge once growth areas land.
- A PATCH that changes nothing returns the node unchanged without bumping. A topic or notes change without `summary` is 422 `summary_required`.
- Reparenting takes `pg_advisory_xact_lock(map_id)` so two concurrent moves cannot build a cycle; the cycle check is a recursive CTE up the parents. The root cannot be moved or deleted alone (422 `root_immovable`); deleting a node deletes its subtree.
- Events survive deletes (no foreign keys); `detail` holds keys and field names only. The validation handler no longer repeats an unknown field name (caller text).
- User author: `user:<who>` from `X-Forwarded-Email`, else `X-Forwarded-User`, else `user:unknown` (agents-vault `actor_of` order and limits: printable, at most 200 chars; the anonymous value is `user:unknown` not `user` because the created_by CHECK needs `user:.+`); delegate callers without a proxy are `user:unknown`. Reads by key (maps, nodes, versions) on web and delegate are unscoped per spec 3.5 (user unscoped, archived projects included); the service listener will read all active projects (2026-11-12). `ProjectLookup` raises `project_unknown` (the spec code; the taskboard copy says `unknown_project`) and lists active slugs for `readable`; Task 9 moves scope into `Actor`.

## 2026-11-12 - scaffold decisions (research-mindmaps Task 7)

- Copy sources: agents-vault (CI, Dockerfile, scripts, mise tasks, OpenAPI export) and agents-taskboard (three listeners: web allowlist, delegate bearer list, service relay bearer). Unlike taskboard, `mindmap serve` runs all listeners in one process with one pool (spec 3.1 "api (three listeners)"); the delegate listener starts only when `MINDMAP_DELEGATE_TOKENS` is set.
- Path prefix `/mindmap/api/v1` on every listener (the agents-web basePath; the ingress routes `/mindmap` without a rewrite, as taskboard does with `/taskboard/api/v1`). The orchestrator relay (Task 15) must target `<mindmap_url>/mindmap/api/v1`.
- Error body follows the siblings: `{"error": {"code", "message", ...extra}}` (the plan line `{"error": code, "message": text}` was read as shorthand for that shape, so web and plugin clients parse one shape across services).
- `idle_in_transaction_session_timeout` is set through the libpq `options` startup parameter on every pool connection (`runtime.open_pool`), not a `SET` in a configure callback: it survives reconnects and leaves no transaction open on a fresh connection.
- Settings: every token pair distinct (secrets invariant 9), the error names both env vars only. Taskboard token required when the taskboard url is set. `public_base_url` is the agents-web host, not the api.
- CLI registers only `migrate` and `serve`; `notifier` (Task 13), `embedder` and `reembed` (Task 21) are registered with their code, so no release carries a stub.
- Tests override the agents_common `pg_url` fixture with `pgvector/pgvector:0.8.7-pg16` (pinned): pgvector must be created by a superuser, as CNPG `postInitApplicationSQL` does live.
- Chart skeleton (superseded by the 2026-11-12 entry: one Deployment per listener): one `api` Deployment (`mindmap serve`, migrate init container), Services `-web` (80), `-service` (8082) and `-delegate` (8081, only with `delegate.tokensSecret.name`), secret values only from external Secrets (no chart Secret). Task 11 completes it (oauth2-proxy sidecar, notifier and embedder Deployments).
- 2026-11-12: one Deployment per listener (`serve-web`, `serve-service`, `serve-delegate`), the sibling pattern of agents-vault and agents-taskboard, replacing the single `mindmap serve` pod. Why: the oauth2-proxy admission webhook protects the first port of the first container of a pod, so listeners sharing a pod could not be told apart, and relay/delegate tokens sat beside the SSO-fronted web listener (secrets invariant 9). Only the web pod carries the oauth2 annotations. Chart env is per component: web gets the orchestrator token; service adds the relay token; delegate adds the delegate list; notifier only the taskboard token and url; embedder and migrate only the database. `MINDMAP_RELAY_TOKEN` is optional in Settings and required by `serve-service` / `create_service_app`. The feed cursor is `after` on both `/events` and `/stream`.

## 2026-11-12 - task notices and the notifier (research-mindmaps Task 13)

- `append_event` is the single choke point: it enqueues the task notices of its map for every kind except `node_embedded` (`EVENT_KINDS`, `SILENT_KINDS` in db/events.py). Edge writes already append one event per map, so both ends enqueue. `link_deleted` notifies only the tasks still linked (the removed one is gone); `map_deleted` cascades the map's pending rows away.
- Migration 0001 edited (service never deployed; release blocked on registry secrets): `task_notices.changes` counts coalesced changes. The notifier marks a row sent only while `changes` is the value it claimed, so a change that lands while the HTTP call is out keeps the row pending and is announced on the next pass (no lost change). Two maps linked to one task share the pending row; its `ref` is the first map's key.
- No transaction across HTTP: `claim_due` runs in a short transaction (FOR UPDATE SKIP LOCKED), the connection returns to the pool, the call goes out, then a guarded `UPDATE ... WHERE status = 'pending'` marks sent, dead (404) or schedules a retry (`attempts + 1`, exponential, capped). Crash before the mark re-sends. 5xx, network errors and other 4xx back off; only 404 is dead.
- The taskboard route is under its prefix: `POST /taskboard/api/v1/tasks/{key}/external-changes` on the delegate listener (Task 12), and it requires a UUID `actor_session`; any other stored value is sent as null.
- Debounce stays configurable: `outbox.configure(settings.notice_debounce_seconds)` runs when an app is created (the API process is the writer); default 60 s.
- Direction fallback: `create_direction` enqueues a `direction_notices` row only when the map has no `T-n` link (checked after the optional task link of the direction is created). The notifier posts `Mind map M-3 got direction D-7: <public>/mindmaps/M-3?direction=D-7` to every active session of the map's project plus superleaders via `SessionLookup` (copied from agents-taskboard without the label filter) and `OrchestratorClient.post_message`; a gone session is skipped, a lookup failure retries the whole notice (a duplicate to sessions already messaged is possible).
- The notifier needs the orchestrator token as well as the taskboard token: chart secrets for the notifier are now taskboard and orchestrator (`EXPECTED_TOKENS` in test_chart updated; the earlier "notifier only the taskboard token" no longer holds). `mindmap notifier` exits 78 without `MINDMAP_TASKBOARD_URL`; `serve()` returns at once in that case.

## 2026-11-12 - reset_all is an accepted second writer of nodes.embedded_rev

- `reset_all` (the `reembed` CLI) runs an unguarded `UPDATE nodes SET embedded_rev = 0`, so it is a second writer of that column besides the embedder's guarded updates. Accepted exception to the one-writer rule: it is an operator-only bulk reset (forces a full re-embed after a model change), never reached by a service path.
- It runs only while embedder work is idle. The embedder stays the only writer of `node_chunks`.

## 2026-11-13 - chart version sha identifier is prefixed with g

- `scripts/chart-version.sh` now prints `X.Y.Z-main.g<sha7>`. Why: a bare all-digit sha7 (CI run 43419200156, sha 0232318) is a numeric semver prerelease identifier; a leading zero is invalid ("version segment starts with 0") and any numeric one compares numerically. The `g` prefix keeps it alphanumeric. `--app-version` still gets the bare sha7.

Why: `POST /maps` with `kind=knowledge` returned 409 `slug_taken` whenever the project already had any knowledge map, because every unique violation was mapped to that code.
